# AI 规划模式 A · GPT 执行计划 v3

更新：2026-10-21。基线 0.3.8。本文是执行契约，实际验收结果另记发布说明。

## 固定边界

- 叠条安排人物、脉络、戏份的节奏，本章规划补充具体事件、动机、冲突与承接。保持整章文字编辑，不增加格子或第四领域。
- 一次生成剧情草稿、结构化建议及 0–3 个问题，不再调用模型总结展示梗概。
- 草稿与采用稿分槽。采用前不覆盖当前计划。未采用剧情及答案不进入正文；生成、修改或恢复新草稿时，旧的有效采用稿仍生效。
- 没有有效采用稿时仍可按当前计划与叠条创作，不能绕过明确矛盾。
- 作者 free_text、misc、character_actions、叠条及设定不被方案操作改写。背景物件继续使用 item。
- 保持正文编辑、细修、导出、正文历史和旧规划 API 语义。

## 数据契约

Chapter 新增稳定 chapter_uid 和独立 SQLite proposal_json，元数据同步。ProposalWorkspace 为 revision（服务端单调递增）、draft（可空）、adopted（可空）。问题、答案不进入 ChapterPlan。

草稿包含剧情、候选计划、问题／作者答案、继承的作者决定、实际输入依据、用量和历史引用。采用稿为不可变快照，另含最终计划、采用时间、依赖指纹与通过凭据。采用后清空草稿；修改采用稿答案先复制新草稿。

问题 ID 服务端生成，最多 3 题；问题 120 字、原因 300 字、选项 3 个、答案 4000 字。模型答案一律不接收。未知 ID 拒绝，空答案可保存和采用。重规划继承原问题与回答，不按题号猜归属。

普通章节保存和旧接口保留服务器最新方案与 UID，不能以旧快照回滚。

统一后端合并函数用于差异预览和提交：

| 字段 | 合并 |
|---|---|
| scene_goal/conflict/stakes/target_word_count | 候选明确提供时替换，否则保留 |
| open_decision_for_user | 保留未决定事项，仅作者明确回答且检查通过才解除对应留白 |
| must_include/must_not | 保留原要求，追加去重 |
| 人物/脉络/戏份 | 保留选择，追加候选与叠条关联 |
| 自由规划/杂项/行动/叠条/设定 | 始终取最新作者值，方案不能写入 |

删除原要求或调整叠条返回原编辑器。

## 接口与并发

前缀 `/project/{project_id}/chapter/{n}`：

| 接口 | 用途 |
|---|---|
| GET /proposal | 双槽、独立状态与原因、差异、当前输入令牌 |
| POST /proposal | 首次、重新或按答案生成 |
| PUT /proposal/answers | 局部保存，必要时从采用稿复制草稿 |
| POST /proposal/confirm | 检查并采用当前草稿 |
| GET /plans、GET /plans/{record_id} | 历史摘要、全文 |
| POST /plans/{record_id}/restore | 恢复为新草稿，保留采用稿 |
| DELETE /plans/{record_id} | 删除非当前引用记录 |

写请求带 chapter_uid、expected_revision、request_id；无方案 revision=0。生成及采用另比较 input_token。响应最新状态与操作结果，客户端只合并操作拥有的字段。

SQLite 持久幂等回执唯一键为作品、UID、request_id。同一请求不重复提交或调用模型，同 ID 不同内容冲突；重启后中断请求不自动重试付费模型。

锁内读取 → 锁外模型 → 锁内复核 UID、revision、输入令牌后合并。正文提交验证正文版本与实际采用稿身份，不因无关草稿保存失效。

## 有效输入与检查

proposal_inputs 统一有效输入、指纹、状态、差异；proposals 编排草稿、答案、采用、历史和提交。路由不另写合并，客户端不计算最终计划。

作者指纹覆盖当前计划、叠条语义、行动、lore_view 实际资料、硬规则、禁忌、风格、相关技能、实际读取的摘要、检索事实及必要衔接原文。方案指纹覆盖剧情、候选、问题／答案和决定。排除纵向布局、选择、窗口、费用和时间。

本章新增正文不直接使采用稿过期，继续参与续写与并发。前章实际衔接内容变化可能失效，不能承诺前章改字永不失效。草稿变化不改变采用稿指纹。

确认检查最终合并后的输入，提交后绑定该输入，避免采用自行过期。只有依赖、方案内容与通过凭据完全匹配才有效。

草稿依据变化时显示原因，不复用原凭据。作者可以明确发起采用检查：使用最新令牌，对当前合并结果完整重查；通过后绑定最新依据，未通过不采用。历史恢复同样处理。

方案的统一输入编译使用无网络的本地历史事实检索，并记录实际选中内容；查看、保存答案及状态检查不会触发远程向量模型。旧规划接口和普通生成的可选混合检索默认行为保持不变。

正文选择：有效采用稿 → 使用采用快照及匹配凭据；否则 → 当前计划与叠条，走普通规划/检查。未采用草稿始终不读；记忆准备、正文校验和并发保护仍执行。

强模型检查方案剧情、作者答案、文字规划、叠条和规则。只阻止双方有原句证据的明确矛盾；缺项、未写明先后、正常过渡不阻止。失败提示未完成，不能当通过。错误携带双方证据和定位，不改作者原文。

## 历史与恢复

文件 `.novel-gm/plans/{chapter_uid}/{record_id}.json`，记录 ID 与方案 ID 不同。生成、采用、恢复及替换前尚未记录的回答留必要记录，自动保存不逐字留历史。最多 30 条，保护草稿与采用稿引用，成功后裁剪。

恢复先备份草稿，再分配新草稿 ID、清除检查凭据，仍有效的旧采用稿继续生效。历史、元数据、数据库和回执接入 pending-save 日志，幂等滚前恢复。目录不可用可查看缓存，禁止需要完整持久化的新写。插章保留 UID，新章新 UID，删除清理该 UID 历史；旧编号结果不能写到另一章。

## 桌面

两处 AI 规划入口与历史共享按作品/UID 绑定的会话和保存队列。打开不自动生成；用户点「生成方案」后才跑模型。已有方案只打开，仅采用稿展示采用稿；无章显示“创建本章”，关闭不建章。

窗口约 900×760，可缩放，沿用主题字体。待采用草稿（含剧情大纲）可直接改并保存。独立显示“正文当前使用的采用稿”及“待采用草稿”。差异来自后端。选项与自由输入共用答案，清空也保存。提供生成方案、按答案再规划、确认并采用、历史和返回规划/叠条入口。

历史沿用正文历史双栏布局，区分当时采用与当前有效，恢复按钮为“恢复为草稿”。保存失败保留输入并可重试，关闭先保存、失败保留窗口；子窗独立关闭。只读章仅查看；AI 期间禁相关修改。三语资源 PlanMode.zh-CN/en-US/ja-JP.xaml。验证浅深主题、窄窗、长文和密集历史。

## 分阶段与交付

| 阶段 | 工作及通过条件 |
|---|---|
| P0 | 基线及判空：只有关联/叠条/字数仍补剧情，自由规划和杂项保留且传入 |
| P1 | UID/双槽/回执/恢复：旧数据空、身份稳定、导入插删正确、旧保存不丢方案 |
| P2 | schema/草稿/问题：一次输出，不填作者答案，不改计划及采用稿 |
| P3 | 编译/合并/检查/采用/生成：矛盾阻止、凭据复用、双槽隔离、旧结果不覆盖 |
| P4 | 历史：双引用保护、恢复只草稿、裁剪与中断恢复 |
| P5 | 桌面/三语/回归/正式包：多窗同步、失败重试、只读、独立关闭、视觉及固定入口 |

测试使用 mock/spy 验证实际输入，覆盖作者保护、双槽隔离、采用有效性及依赖变化、纵向不失效、0/1/3 题及超限/清空/未知 ID/继承/未答/主角留白、证据检查及失败、幂等、模型期间修改、插删章、重启、目录丢失、旧客户端及原功能回归。
